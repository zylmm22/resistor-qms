## 2. 设计

### 2.1 唯一来源

| 层 | 来源 | 说明 |
|---|---|---|
| 特性字典 `char_master` | 共享主数据 | 新增/修改后只同步“仍与旧主数据一致”的项目副本，项目已确认的特定规范不被覆盖（响应的 `propagation` 报告生效与保留数量） |
| 项目特性 `project_char` | **项目内唯一规范来源** | P2-11 批准、特性主数据变更、人工调整都落到这里 |
| CP 行 `cp_row.project_char_id` + `spec_text` | 下游引用 | SPC/MSA 一律通过 `cp_row.project_char_id` 读取，不再优先用监控项自身快照 |
| MSA 计划 `msa_plan_item` | 快照 | 未完成计划随规范刷新快照与公差；已完成研究保持历史证据 |

### 2.2 P2-11 全字段同步（D-03）

`lib/deliverable-sync.js` 的 `special-characteristic` 规则原先只写 `tol_text`，现在同步 `unit/target/lsl/usl/tol_text`：

- 优先级：`_syncMeta.chars[rowId]` 显式数值 > 「规格/公差」文本解析 > 已确认项目特性 > 特性字典；
- 文本解析器 `parseSpecification` 支持 `10±0.1`、`10 +/- 0.1`、`10 +0.1/-0.2`、`9.9~10.1`、`10 mm`、纯数值；
- 解析只补缺，不覆盖 P2-11 行或字典里已显式维护的数值；
- `tol_text` 为空时用数值生成 `lsl ~ usl unit`，保证下游永远有可读规范。

### 2.3 规范变更收敛（D-03 / Q-09）

`server.js` 新增 `reconcileCharacteristicSpecs(projectId, pcharIds)`，在 `syncProjectDeliverables` 内、同一事务中执行：

1. 找到该特性的全部 CP 行（按 `project_char_id`，或旧式 `char_id`）；
2. `cp_row.spec_text` 与项目特性同值——**显式 `override_fields_json` 含 `spec_text` 的行保留人工值**；不可解析的历史自由文本（如“见顾客图纸”）不静默覆盖；
3. 规范确实变化的 CP 表头降草稿（先写 `cp_revision` 快照）；
4. 关联 `monitoring_item` 回到待审核并重新挂到当前项目特性（即使 CP 行保护了文本）；
5. 未完成的 `msa_plan_item` 刷新名称/单位/目标/上下限/公差快照并标记待复核；已完成研究不动。

同步结果新增 `spec` 计数（`characteristics / cp_rows / monitoring_items / msa_plans`），特性主数据 PATCH 额外返回 `propagation`（受影响项目、项目特性数、保留的人工值数），审计 `after` 中记录。

启动时的全项目同步改为 `reconcile:false`：只刷新引用与同步记录，不因历史数据格式差异批量降级已批准控制计划。

### 2.4 C-04：抽样要求与 SPC 配置分离

`POST /api/cp/:row/monitor` 不再回写 `cp_row.sample_size / freq_value / freq_unit`，只回写 `is_spc`、检具与特性关联。CP 的样本容量、抽样频率由控制计划维护，监控项的子组大小与抽样配置只读影响 SPC。

### 2.5 M-07：空公差不再卡死

`POST /api/msa`：

- 一致性校验改为 `plan.tolerance != null && +body.tolerance !== +plan.tolerance`；
- 计划公差为空时，允许使用本次填写的正数或项目特性 LSL/USL 差，**并写回计划**；
- 计划与输入都无有效公差时，文案明确指向“计划尚未维护公差”，不再误报“研究设计必须与计划一致”。

### 2.6 Q-09：监控项不再持有过时特性

`/api/cp/row/:id/characteristic` 重挂特性时，关联监控项同步改挂新项目特性并回到待审核；`/api/spc`、`/api/spc/:id`、`/api/monitoring/pending` 的规范化 `COALESCE` 顺序改为 `cp_row.project_char_id` 优先，CP 重映射后立刻读到新规范。

### 2.7 数值精度

MSA 公差统一 `toFixed(10)`，避免 `10.2-9.8` 写成 `0.3999999999999986` 导致重复同步与显示不一致。

## 4. 验证

```
node tests/p1-2-spec-penetration.js
P1-2 characteristic specification penetration tests passed (34 checks)
```

覆盖场景：

1. 字典创建 → 引入项目 → CP 行自动带出规范文本；
2. 监控项 I-MR（子组 1、频率 4h）创建后 CP 仍为样本容量 5、频率 2h（C-04）；
3. 初始 SPC/MSA 规范与项目特性同值，GR&R 使用计划公差 2；
4. 修改特性主数据 `lsl/usl/tol_text` → 项目特性、CP 文本、SPC 详情、MSA 快照/公差同值，CP 降草稿，监控项待审核（D-03）；
5. 复核后 SPC/MSA 再次同值，新 GR&R 使用新公差 1；
6. 直接调整项目特性规范 → CP 文本与 MSA 快照跟随；
7. P2-11 录入 `20±0.4 mm` → 项目特性得到 target/lsl/usl/unit/tol_text，CP 行与 MSA 计划同值并待复核；
8. 空公差计划：不填公差被拒且文案指向计划；填 4.5 后计算成功并写回计划（M-07）；
9. CP 行重挂另一特性 → 监控项回到待审核，SPC 详情立即读到新 LSL/USL（Q-09）；
10. 项目特性已人工确认时，字典修改保留项目值并计入 `preserved_local`；
11. 不可解析的自由文本规范不被静默覆盖，但 MSA 仍采用项目特性数值；
12. 审计流包含特性主数据修改事件。

`npm test` 全量通过（smoke、linkage 168 项、ocr、三套 UI 逻辑、P0 验收 20/20、PFD 派生 56 项、P1-2 34 项）。
