## 二、我采纳的三件事

### 1. 三级菜单（模块 → 阶段 → 功能页）

原来的左侧是扁平 10 项，业务上找不到"我在哪个阶段的哪个活动"。已改为：

```
项目 → 仪表盘 / 管理驾驶舱 / 预警中心
APQP → 阶段管理 / 门径评审 / 变更管理
专业工具 → FMEA / PFD / CP / SPC / MSA / PPAP
追溯与治理 → 特性穿透 / 关联结构树 / 基线与变更
```

「阶段管理」里每个阶段卡片上方有一排功能页签，点签子直接跳到对应交付物或工具。这是**信息架构层面**最值得抄的一点：用户按"阶段 → 活动"找东西，而不是按"功能模块"找。

### 2. 门径评审与阶段解耦

对方把"阶段进度"和"Gate 评审"做成两件事——阶段是时间轴，Gate 是决策点，Gate 通过才允许进入下一阶段。我原来只有阶段没有 Gate，等于没有"卡点"。

已实现 Gate 0–5：每道门有 3–4 条硬性检查项、评审意见、通过/驳回记录；**检查项未全部满足时不允许判"通过"**（后端校验）。通过后自动推进项目阶段并写审计流。

### 3. 预警中心（从数据自动产生，而非人工登记）

对方的预警中心有 6 类：FMEA 高风险、8D 未关闭、ECR 待审批、门径待评审、Phase 进度偏差、PPAP 批准率。

我实现为**后端聚合计算**，不新增"预警表"——预警是状态推导出来的，不是人填的：

| 预警 | 触发规则 | 为什么这样定 |
|---|---|---|
| FMEA 高风险 | AP=H 且无处置决定 | 见第四节（AP 而非 RPN） |
| 文档待审核 | 状态 = 待审核 | 对应对方的"已批准/待审核/草稿"三态 |
| 门径待评审 | 当前阶段及以前存在未通过的 Gate | 对方叫"门径评审待评审提示" |
| MSA 不合格 | %GRR > 30 或从未做 | 挂在检具台账上 |
| SPC 能力不足 | Cpk < 1.33 | 对方无此项，是我加的（因为它直接影响售后） |
| ECR 待审批 | status = 待审批 | 对应对方"ECR 待审批" |

不建预警表的理由：一旦落表就要人工维护状态（已读/已处理/忽略），半年后必然与真实数据脱节。派生计算永远准确。

| 功能 | 差异 |

| FMEA 七步法 | 我按 AIAG-VDA 2019（AP），对方用 **RPN ≥ 100** 预警——见第四节 |

### 暂缓（对方有、我标记为"规划中"，共 6 项）

| 功能 | 为什么暂缓 |
|---|---|
| SOP / SIP 自动生成 | 有价值，但依赖控制计划的字段结构化程度；我的 CP 已具备（样本/频率/反应计划已拆字段），可以做的时机成熟 |
| Run@Rate 产能验证 | 属于制造工程域，需要节拍、瓶颈、爬坡数据，与"质量体系"耦合度低于前几项 |
| 供应商 VDA6.3 | 是独立子系统（供应商评估 + 不符合项跟踪），体量与 APQP 相当，硬塞进来会做浅 |
| 报表中心（26 图表） | 我现在是"每个页面自带图表"，缺"自定义报表"——但报表中心的价值取决于客户是否真的会配，先不做 |
| 甘特图 | 只有简化版（交付物计划条），真正的甘特需要任务依赖与基线对比 |
| 用户与权限（5 角色） | 单机演示系统没有真实鉴权，做了也是假的 |

### 明确不做（对方有但我不建议抄）

| 功能 | 不建议的理由 |
|---|---|
| **RPN ≥ 100 自动标记高风险** | 这是第二版遗留。AIAG-VDA 2019 已用 AP 替代 RPN，且 RPN 有结构性缺陷（S=10,O=2,D=5 与 S=2,O=5,D=10 同为 100）。我坚持用 AP 查表，并在评审文档里写过理由 |
| **"13 个交付物"** | 这个数字对甲方是营销口径，对乙方是桎梏。第三版是 52 个输入输出，砍到 13 会漏项；我按第三版保留 75 项可跟踪项，用"输入/输出/活动/检查表"分组降低噪音 |
| 三级菜单里塞 51 个页签 | 我采纳了页签形式，但**不是每个页签都做成独立数据表**——大部分页签直接指向同一份交付物或同一个工具，避免"页面很多、数据很散" |

## 四、逻辑关系上我做的一处修正

对方的预警规则是 **"FMEA 高风险预警（RPN ≥ 100 自动标记）"**。

这是第二版 FMEA 的做法。AIAG-VDA 2019 明确用 AP（Action Priority，高/中/低）替代 RPN，原因是 RPN 把三个维度当成等权相乘：
- S=10, O=2, D=5 → RPN 100
- S=2, O=5, D=10 → RPN 100

两者风险完全不同，却得到同一个数。用 RPN ≥ 100 做预警线，会把大量"低严重度但难探测"的项误报为高风险，同时漏掉"高严重度但 O 很低"的真实风险（后者恰恰是安全件最该盯的）。

我的实现：`AP=H 且无处置决定` 才进预警，且 AP 由 S/O/D 查矩阵得出，不计算乘积累加。这条差异在客户审核时是加分项（能解释为什么不用 RPN），而不是减分项。

## 五、还没补上的逻辑缺口（下一步优先级）

| 优先级 | 缺口 | 影响 |
|---|---|---|
| P0 | **闭环视图**：DFMEA-DVP&R 闭环、PFMEA-CP 闭环 | 对方把"闭环"做成独立页面（显示 FMEA 行 → 验证项 → CP 行的对应关系与缺口）。这是我"关联结构树"的下一步：不只给关系，还要给**缺口** |
| P0 | **文档三态**：草稿 / 待审核 / 已批准 | 我只做了 未开始/草稿/已完成，缺"待审核"这一环，导致审批流立不起来 |

| P2 | SOP/SIP 生成 | CP 字段已结构化，可以出模板 |
| P2 | 角色与权限 | 演示系统可暂缺，上生产必须有 |

## 六、一句话总结

对标对象最值得学的不是功能数量，而是**"以阶段和门径组织信息、以预警驱动日常动作"**这两条产品逻辑；最不该学的是**用 RPN 做风险判定**——那是标准已经淘汰的方法。功能上我补了门径、预警、变更、驾驶舱四块，砍掉了供应商与报表中心的照搬，把"51 个页签"落到 6 个阶段的可跳转入口上。
