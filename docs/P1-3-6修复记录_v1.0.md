## 2. P1-3：PFMEA ↔ CP 硬关联

### 2.1 C-11 批准门

`validateCpForApproval(cpId, projectId)`（`server.js`）：

- 只对 **PILOT / SOP** 控制计划生效；原型 CP 允许先于 PFMEA 建立。
- 逐条活动 CP 行判断：
  - 特殊特性（`project_char.is_special` 或 `char_master.is_special`）；
  - 或该工序/特性在 PFMEA 中存在 `ap='H'` 的行。
- 上述行必须在 `cp_fmea_link` 或 `cp_row.fmea_row_id` 中指向本项目 PFMEA 的现存行，否则返回 409 + `details.cp_rows`。
- `POST /api/cp/row` 新增可选 `fmea_row_id`：校验归属与工序一致，并写入 `cp_fmea_link`。

### 2.2 F-05 决定快照

- `fmea_decision` 新增 `s/o/d/ap/decided_at` 列（`ensureColumn` 迁移）。
- 提交/批准决定时写入当前行快照；批准时若快照与行不一致返回 409。
- `POST /api/fmea/row` 修改行且 S/O/D/AP 变化时，已批准决定自动回到“待评审”，审计记录旧/新风险值。
- `POST /api/fmea/publish` 的高 AP 门禁同时比对快照。

### 2.3 F-06 删除清理

P0-4 已实现：删除 FMEA 行/节点/清空时会清理 `cp_fmea_link` 并把受影响 CP 降草稿。本批补充了端到端回归用例。

## 3. P1-4：PPAP 质量门

### 3.1 B-04 质量门

`ppapWorkflowRows` 的 `ready` 由“存在”改为“合格”：

| 来源 | 新判定 |
|---|---|
| FMEA | 已发布，且高 AP 行都有已批准、快照与当前 S/O/D 一致的决定 |
| MSA | 所有活动计划完成、来源有效，且关联研究判定为“接受” |
| SPC | 每个已批准监控项有数据，Cpk ≥ `cpk_target`，控制图无判异信号（P/C 图只判稳定性） |
| PFD / CP / 文档 | 沿用原有发布/批准条件 |

- 新增 `ppap_deviation` 表与接口：
  - `POST /api/ppap/deviations`（原因≥10 字、可选有效期）；
  - `PATCH /api/ppap/deviations/:id`（质量角色、禁止自批、驳回需原因）。
- 已批准且未过期的偏差使对应要素 `gate_ready=true`；打包清单、README 与 `manifest.json` 记录所用偏差。
- `PATCH /api/ppap/:no` 标记完成时对 FMEA/MSA/SPC 复用同一质量门。

### 3.2 B-02 等级矩阵

| 等级 | 要求提交要素 |
|---|---|
| 1 | 18（PSW） |
| 2 | 1,2,3,9,10,12,13,14,17,18（PSW + 样品 + 有限支持数据） |
| 3 | 全部 18 项 |
| 4 | 18 + 顾客指定（`ppap_submission.required_items_json`，PATCH `required_items`） |
| 5 | 全部 18 项（现场审核） |

`GET /api/ppap` 返回 `level_requirements`，页面可按等级展示实际清单；打包使用同一函数。

### 3.3 M-02 判定

`computeGRR`：

- `GRR=0` → “接受（无变差）”；
- `ndc<5` → “不接受（不足以用于控制）”；
- 再按 `%Overall` 分 10%/30% 两档；
- 返回 `reason`，前端 KPI 颜色与 ndc 卡片直接取该结论。

### 3.4 M-13 来源失效

`/api/msa` 为每个研究计算 `source_invalid` / `source_invalid_reason`（计划已替代、待复核或来源失效）；PPAP 只统计 `source_active` 计划，失效研究不计入证据。

## 4. P1-5：Gate/阶段统一

### 4.1 S-01 单一结论函数

`lib/logic.js` 新增 `gateStatus(projectId, criteriaVersion)`：

- 旧版本 `criteria_version` 的记录统一返回 `decision='待复核'`、`needsRevalidation=true`；
- `canReview` 取决于前一道 Gate 以当前版本通过；
- `passed` 只统计**连续**通过的 Gate。

`GET /api/gates`、`L.alerts`、`L.cockpit` 全部调用该函数；驾驶舱 `gatePassed` 不再计入旧版通过。

### 4.2 S-06 阶段派生

- Gate 评审写入后重新计算 `derivedPhase = min(5, 连续通过的 Gate 数)` 并写回 `project.phase`；
- 驳回/重开会回退阶段；
- APQP 任务完成度不再直接改 `project.phase`（只更新 `apqp_phase.status`）。

### 4.3 S-07 阶段名称

`public/app.js` 的 `phaseName` 改为与 `project.phase`（0–5）一致的 0-based 数组：组织与准备 / 策划和定义项目 / 产品设计和开发 / 过程设计和开发 / 产品和过程确认 / 反馈、评定和纠正措施。

## 5. P1-6：ECR 落地

### 5.1 E-01 结构化变更

- `change_item` 新增 `field_name/old_value/new_value/applied_at/applied_by/applied_result`。
- `POST /api/ecr` 接受 `changes: [{object_type, object_id, field_name, old_value, new_value}]`，创建时即校验字段白名单与对象归属。
- 自动变更白名单：
  - `project_char`：name/description/unit/target/lsl/usl/tol_text；
  - `cp_row`：spec_text/measure_tech/sample_size/freq_value/freq_unit/control_method/reaction_plan；
  - `fmea_row`：s/o/d/pc_text/dc_text（改 S/O/D 时后端重算 AP 并失效原决定）；
  - `process_step`：name/equipment/fixture/input_desc/output_desc。
- `/apply` 在事务中逐项比对旧值 → 更新 → 标记执行人/时间；任一旧值不符返回 409 并整单回滚；随后同步下游、生成 `ECR <id> 实施快照` 基线。
- 未纳入白名单的对象不会被猜测执行，接口返回明确提示。

### 5.2 E-03 状态前置条件

- 批准：必须存在结构化变更/受影响对象，或不少于 10 字的影响分析；
- 关闭：必须已实施、存在变更后基线、所有结构化变更项已执行，并填写验证结论；
- 所有迁移继续写审计。
