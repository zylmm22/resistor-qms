## 一、这个系统是什么

`resistor-qms` 是一套面向车规电阻器（金属膜固定电阻器）的**APQP 全流程质量管理原型系统**，用一套原生 Node + 原生 JS 单页应用实现了 AIAG APQP / VDA FMEA / SPC / MSA / PPAP 的主要工作流。

### 1.1 功能模块

| 模块 | 功能 |
|---|---|
| 项目与阶段 | 多项目管理；APQP 阶段 0–5；68 项交付物目录（49 个在线表单、9 个系统模块、10 个输入/活动项）；阶段 Gate 评审（检查项 + 结论 + 意见） |
| 交付物 | 在线表单编辑（字段/表格/检查表）；自动保存；Word/Excel 导出；DOCX/XLSX 模板上传与在线编辑；字段映射；提交→审核→批准→修订；版本历史；完成度 |
| PFD | P1-10 初始流程图（INITIAL）、P3-04 过程流程图（PROCESS）；工序/工步树；矩阵视图；图片 OCR；批量导入；发布/撤回；排序 |
| FMEA | DFMEA/PFMEA；七步法结构树（结构→功能→失效）；FE/FM/FC 节点；AP 矩阵；S/O/D 三场景；措施；AP=H 决定；发布门禁 |
| 控制计划 | 三阶段（原型/试生产/量产）；CP 行（工序/特性/规范/抽样/控制方法/反应计划）；与 FMEA 关联；批准/冻结；安全投产 |
| SPC | 监控项（Xbar-R/Xbar-S/I-MR/P/C）；手工录入与 Excel 导入；控制图；8 条判异；Cp/Cpk/Pp/Ppk；监控项审批 |
| MSA | 检具台账与校准；MSA 计划（从已批准 CP 派生）；均值-极差 GR&R；外部报告登记；判定 |
| PPAP | 18 项要素；提交等级；就绪校验；冻结基线；ZIP 打包与哈希；导出记录 |
| 基线与变更 | 不可变基线快照；对象级/字段级 diff；ECR 变更单与分支基线 |
| 特性与字典 | 特性主数据、项目特性、产品↔过程特性 M:N 穿透；工序字典；特性来源 |
| 平台 | 登录/角色（admin/engineer/quality/auditor）；`?p=` 项目切换；审计；总览/预警/驾驶舱；质量工具导出 |

### 1.2 设计上的优点

- 业务建模覆盖完整：从 APQP 交付物到 PFMEA→CP→SPC/MSA→PPAP 的主线对象齐全，且大量规则确实落在服务端（不是纯展示）。
- AP=H 必须有已批准决定、FMEA 发布要求叶节点有正式功能与分析行、CP 行删除有引用保护、PPAP ZIP 下载校验哈希——这些是同类原型里少见的“真门禁”。
- 计算核心的选择正确：Xbar-R/Xbar-S/I-MR 的 σ 估计、Cp/Cpk 用组内 σ、Pp/Ppk 用总体 σ、单边规范处理、GR&R 的 EV/AV/%Tol/ndc 公式，均与手册一致（详见附录 A）。
- 零依赖、单文件数据库、手写 OOXML/ZIP，部署成本极低，适合演示与咨询交付。

### 2.2 五条系统性根因

这不是 130 个孤立 bug，而是五类反复出现的设计缺陷：

**根因 1：身份不是“会话事实”，而是“请求参数”**

`body.approved_by`、`body.reviewer`、`body.user` 可以决定谁批准了什么；更多路径直接用固定姓名（“张工艺”“质检-陈”“质量经理 王”“设计-陈”）。角色只实现了“auditor 只读 / 其他人全可写”，`engineer` 与 `quality` 权限完全相同。**后果：所有受控记录（交付物版本、CP 批准、FMEA 决定、PPAP、基线）都无法证明审批人。**

**根因 2：同一事实存在多套口径**

- Gate 是否通过：接口按检查表版本判，预警/驾驶舱按旧记录判（S-01）。
- 阶段完成度：三套分母（S-13）。
- MSA 是否可接受：后端 `judgment` 与前端颜色两套逻辑（M-02）。
- 项目数据：多条聚合与快照查询没有项目过滤（S-02）。

**根因 3：写操作缺少“前置校验 + 事务边界”**

`markCpDraft` 在校验前执行（C-02）、监控项创建即自批（C-03）、任何 CP 编辑都写覆盖标记（C-01）、批量导入直接作废在用工序（P-07）、删除 FMEA 行不清 `cp_fmea_link`（F-06）、`DB.tx()` 对 async 回调提前提交（S-16）。**后果：失败路径也改变数据，且难以回滚。**

**根因 4：导出/打包信任“当前状态”，而不是“受控版本”**

交付物导出读当前 `data_json` 却用旧版本号（A-01）、PPAP 打包取“最近任意基线”（B-01）、清单用实时状态而包里装基线快照（B-03）、导出记录挂最近基线（B-11）。**后果：受控文件与证据包不可信。**

**根因 5：主线对象之间只有“软关联”，没有“来源约束”**

P1-10 与 P3-04 是两套工序（P-06）、CP 行可无 PFMEA 依据（C-11）、特性规范只同步文本（D-03）、PPAP 只看证据“有没有”不看“行不行”（B-04）。**后果：APQP→PFMEA→CP→SPC/MSA→PPAP 的数据链在关键节点断掉。**

### 2.3 对用户的三句话结论

1. **作为演示/培训原型，它已经能完整走通 APQP 全流程**，业务对象和大部分门禁是真实的，不是空壳。
2. **作为受控质量系统，目前不能用于真实 PPAP 提交**：审批身份、受控版本、控制图/GR&R 计算口径、PPAP 质量门这四项都还达不到审核要求。
3. **修复不需要重写**：数据模型基本正确，问题集中在“状态机守卫、口径统一、引用完整性、导出取数”四类，可按下面的路线图分批收敛。

### 4.3 五处必须打通的断点

> **状态说明（2026-11-05）**：以下五段是审查时的断点描述，对应的 P-06/P-02、D-03/C-04/M-07/Q-09、C-11/F-06、B-04/M-13、A-01/B-01/B-03/B-11 均已在 P0～P3 批次修复；当前实现见各明细状态头与第五节 v1.6 收口状态。

#### 断点 1：P1-10（INITIAL）与 P3-04（PROCESS）是两套数据

- **证据**：`deliverable-sync.js:1073-1075` 把 P1-10 的工序写入 `pfd_mode='INITIAL'`；`control-sync.js:80/154/191/243/251` 只读 `pfd_mode='PROCESS'`；`doctpl.js:500/527` 分别把 P1-10、P3-04 指向两个模式。
- **后果**：阶段 1 的初始工序路线对阶段 3、PFMEA、CP、SPC 没有任何贡献；两套工序号/名称可以互相矛盾；用户要在阶段 3 重新录入。
- **修复**：P3-04 提供“从 P1-10 生成/继承”，保留 `origin_step_id`；INITIAL 作为 PROCESS 的来源或父级；一致性检查覆盖两层；下游继续只用 PROCESS。

#### 断点 2：特性规范只穿透了“文本”，没有穿透“数值”

- **证据**：`deliverable-sync.js:1135-1137` 只写 `tol_text`；`cp_row.project_char_id` 与 SPC 读取 `lsl/usl/target`，但这些字段没有从 P2-11/特性主数据同步。
- **后果**：CP 显示“10±0.1”，SPC 的 `lsl/usl` 却是空 → Cpk 为 `null`（Q-03/Q-12 的显示问题由此放大）；MSA 的 `tolerance` 为 `null`（M-07）。
- **修复**：把 `lsl/usl/target/unit/tol_text` 作为一个整体同步；`project_char` 为唯一规范来源；修改触发下游“待复核”。

#### 断点 3：CP 与 PFMEA 只有“可选的软链接”，删除还不清理

- **证据**：`server.js:3664-3700` 创建 CP 行不要求 `fmea_row_id`；`server.js:3324-3331/3391-3395` 删除 FMEA 行只 `UPDATE cp_row SET fmea_row_id=NULL`，不删 `cp_fmea_link`；`server.js:3712` 又用 `cp_fmea_link` 阻止 CP 行删除。
- **后果**：CP 可以脱离 PFMEA 存在；PFMEA 删除后 CP 仍显示已批准；孤儿链接让 CP 行永远删不掉。
- **修复**：高 AP/特殊特性行强制关联；删除 FMEA 行时清理链接并把 CP 置草稿；CP 就绪检查增加“未关联 PFMEA 行”项。

#### 断点 4：SPC/MSA 的“有效性”没有进入 PPAP 门禁

- **证据**：`server.js:5135-5188` 的 `sourceType` 就绪校验：MSA 只要计划全部完成（不看 `judgment`），SPC 只要有数据集（不看 Cpk/判异），FMEA 只要已发布（不看决定是否失效）。
- **后果**：`%GRR=45%`、`Cpk=0.6`、控制图失控的项目也能打 PPAP 包。
- **修复**：质量门配置化：MSA `judgment='接受'`（条件接受需偏差批准）、SPC `Cpk≥目标` 且无失控、FMEA 无未关闭高 AP；不满足时阻止或要求书面偏差（原因+批准人+有效期）。

#### 断点 5：导出/打包/基线三者不同源

- **证据**：交付物导出读 `row.data_json`（A-01），PPAP 打包取最新基线（B-01），清单用实时状态（B-03），导出记录挂最近基线（B-11）。
- **后果**：客户拿到的 ZIP 与“提交时审查的那一版”不是同一份；草稿可能以批准版本号流出。
- **修复**：一切受控输出绑定“对象 + 版本/revision + baseline_id”；打包前回读校验；导出记录写真实版本。

11. 冻结新基线后打包仍取提交基线（B-01）。
12. 删除 FMEA 行后 `cp_fmea_link` 为空（F-06）。
13. PFD 批量替换被引用工序时拒绝或要求迁移（P-07）。
14. 两项目并存时总览/审计/基线不串数据（S-02）。
15. 检查表升版后 Gate/预警/驾驶舱结论一致（S-01）。
