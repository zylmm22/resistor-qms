## 1. 验收方法

新增 `tests/p0-acceptance.js`，把修复记录第 8 节的五批手工步骤固化为可重复执行的集成测试：

- 以 `PORT`、`QMS_DB_PATH`、四个 `QMS_*_PASSWORD` 启动真实服务，轮询 `/api/meta` 等待就绪；
- 四个角色（admin / engineer / quality / auditor）分别登录，用各自 Cookie 调用接口；
- 每项检查独立记录 PASS/FAIL 与失败原因，结束时打印汇总表，失败则以非零码退出；
- 同时新增 `tests/p0-acceptance.js` 覆盖“未配置口令”的冷启动场景：另起一个不传 `QMS_*_PASSWORD` 的进程，检查一次性口令文件、启动告警与真实可登录性。

重跑方式：

```bash
npm run test:p0
```

`npm test` 已把该套件串入末尾，后续回归会自动执行。

## 3. 验收中发现并修复的产品缺陷

| # | 缺陷 | 影响 | 修复 | 复验 |
|---|---|---|---|---|
| 1 | 质量工具导出（`/api/quality-tools/:tool/export`）在**未受控**时，文件内已标 `【未受控】`、版本已加 `(未受控)`，但写入 `export_event.object_version` 的仍是 `control.version`（如 `r1`） | 导出台账无法区分“当时导出的是草稿还是批准版”，与 P0-5“导出记录可追溯”的目标不符 | `server.js` 质量工具导出记录：受控时取 `control.version || payload.version`，未受控时取标注后的 `payload.version`（含 `(未受控)`） | P0-5.3 通过：草稿记录含 `未受控`，批准记录不含 |

### 验收过程中确认的“非缺陷”

以下三处最初表现为失败，经核对为**测试假设错误**，不是产品缺陷：

1. **控制计划编号是动态生成的**：`CP-<项目内部 ID 后 10 位>-<阶段>`，不是 `CP-<项目编号>-<阶段>`。验收脚本改为创建项目后从 `GET /api/cp` 读取真实编号。
2. **演示数据 CP-00030 的 `override_flag` 本来就是 1**（种子数据里的历史“客户要求改频次”示例）。验收“普通编辑不写覆盖标记”必须选一条初始未覆盖的行（CP-00025）。
3. **已批准控制计划的导出不带【未受控】是正确行为**，首次验收误用已批准的 PROTO 阶段去验证“未受控标记”；改为草稿 SOP 阶段验证，并补充“已批准导出不得带未受控”的反向断言。

## 4. 未覆盖项与残余风险

| # | 项 | 说明 |
|---|---|---|
| 1 | 人工浏览器验收 | 未在真实浏览器中逐屏点击 CP“版本历史”抽屉、409 影响面确认框、SPC 审批确认框。对应 DOM 逻辑测试通过，但渲染/事件绑定仍建议人工过一遍 |
| 2 | 真并发 | 乐观锁用“旧 token 再保存”模拟并发，未用两个真实进程/标签页同时提交。语义等价（服务端只比对 token），但不是压力验证 |
| 3 | 隔离覆盖范围 | 项目隔离按“新项目总览/审计/基线/成员”验证；未逐一验证 SPC、MSA、PPAP、Gate、驾驶舱等每个页面在双项目下的展示 |
| 4 | 兼容模式 | `canAccessProject()` 在项目**未配置成员**时仍对全部账号开放。P0-2 只保证“配置了成员即隔离”；生产部署前必须为每个项目配置成员，或改为默认拒绝 |
| 5 | 遗留事项 | P0 修复记录第 7 节 10 项遗留（`char-links` 全局、D-03 特性规范穿透、前端演示姓名残留、`recordApproval` 死代码、`cp_row`/FMEA 行无并发控制等）状态不变，属 P1/P2 |
