## 本模块结论

MSA 的**公式本身**（EV/AV/GRR、`%Tol=6·GRR/公差`、`ndc=1.41·PV/GRR`）实现正确，但**常数表用错**，导致所有结论系统性偏乐观；再加上 `ndc` 门槛位置错误，判定结果不可直接用于 PPAP。PPAP 侧的核心问题是“就绪只看有没有、不看行不行”，以及“打包取的基线不是本次提交对应的基线”。

## MSA

### M-01 【高】【逻辑】GR&R 常数未按 AIAG K1/K3 取值，PV/EV 系统性偏大

- **位置**：`lib/db.js:866`（`d2t`）、`lib/db.js:888-892`（`d2p`）
- **现象**：
  - `d2p` 直接使用普通极差系数 d2（2–10 件：1.128/1.693/2.059/…/3.078），而 AIAG 均值-极差法的 K3 倒数为 1.414/1.912/2.239/2.481/2.672/2.830/2.963/3.078/3.179。`PV=Rp/d2p` 因此被放大：10 件 +3.3%、5 件 +6.7%、3 件 +12.9%、2 件 +25.4%。
  - `d2t` 在 `trials=5` 时取 2.326，AIAG K1=0.4030（倒数 2.481），EV 被放大 6.7%。
  - 同一函数的 `d2o` 却用了 K2 的准确值（1.41/1.91/2.24/2.48），口径自相矛盾。
- **触发/影响**：TV 随 PV 放大，`%GRR/%EV/%AV` 偏小、`ndc` 偏大；默认 10×3×3 的演示与常态研究整体偏乐观，可能把“不可接受”判成“接受”。
- **建议**：`d2p` 换成 K3 倒数表；`d2t` 的 5 次改为 2.481；增加以 AIAG 手册示例为基准的回归测试，锁定 `%GRR/ndc`。

### M-02 【高】【逻辑】`ndc` 门槛位置错误，判定与前端配色两套口径

- **位置**：`lib/db.js:901-903`；`public/app.js:6422-6428`、`6496`
- **现象**：`judgment = pctOverall < 10 && ndc >= 5 ? '接受' : pctOverall <= 30 ? '条件接受' : '不接受'`。`ndc<5` 只在“<10%”分支里生效，永远不会导致“不接受”；`GRR=0` 时 `ndc=0`，反而判“条件接受”。前端 KPI 颜色只看 `pctGRR`（<10 绿、≤30 黄），与 `judgment` 独立。
- **触发/影响**：`%GRR=8%、%Tol=45%` → 结论“不接受”但 KPI 绿色；`%GRR=8%、ndc=3` → “条件接受”+绿色，而 AIAG 要求 `ndc≥5` 才可用于控制。
- **建议**：判定收敛为单一函数返回 `{judgment, reason}`：先判 `ndc<5` → 不可接受（或“不可用于控制”），再按 `%GRR/%Tol` 分级；`GRR=0` 单独判“接受（无变差）”；前端颜色直接取 `judgment`。

### M-03 【高】【操作】非“接受”的研究把计划永久卡在“研究中”

- **位置**：`server.js:4321-4329`（`PATCH /msa/plans/:id` 的 `fields` 白名单不含 `status`）、`server.js:4446-4450`（只有“接受”可完成）
- **现象**：新建研究后计划置“研究中”；只有 `PATCH /msa/:id/complete` 且判定为“接受”才能变“已完成”。白名单不含 `status`，4321 行却用 `body.status` 做“已完成不能回退”的守卫——这段守卫是死代码，即使传 `status` 也被静默忽略。
- **触发/影响**：判定为“条件接受/不接受”的研究，计划永远“研究中”，既不能重做也不能关闭。
- **建议**：把 `status` 纳入白名单并只允许 `计划 ⇄ 研究中` 的合法迁移；或增加“评审不通过 → 退回计划”动作并写审计与原因。

### M-04 【高】【逻辑】演示 `msa_study` 没有项目关联，且回填语句在 seed 之前

- **位置**：`lib/db.js:747`（INSERT 列不含 `project_id/project_char_id/char_id`）、`763-764`（`UPDATE` 回填）、`1649-1660`（先回填、后 `if (row.c===0) seed()`）；`server.js:4269-4276`（`WHERE ms.project_id=?`）
- **现象**：回填执行时表为空；seed 插入的 G-014/G-021 永远不会被回填；首次启动的演示项目“历史研究”恒为 0 条。
- **触发/影响**：README 宣称的 MSA 演示数据实际不可见；用户以为模块坏了。
- **建议**：seed 时直接写入项目与特性关联；或把回填移到 `seed()` 之后；对已有库补一次迁移。

### M-05 【中】【操作】已完成研究可被直接删除，无引用保护

- **位置**：`server.js:4368-4383`；`public/app.js:6632`、`6664-6671`
- **现象**：`DELETE /api/msa/:id` 只要求研究存在；删除后把关联计划退回“计划”并清空 `completed_at`，不检查 PPAP 提交或基线引用；前端只有通用确认。
- **触发/影响**：删除一条已确认完成的“接受”研究，会直接抹掉审核证据链（只剩一条 audit），PPAP 包里的 MSA 报告失去依据。
- **建议**：`status='已完成'` 或存在 PPAP/基线引用时拒绝删除，改为“作废”并保留记录；删除前列出受影响对象。

### M-06 【中】【逻辑】检具编辑不做编号唯一性校验，校准到期日可清空且无提示

- **位置**：`server.js:4513`（POST 有 code 唯一性校验）对比 `server.js:4526-4551`（PATCH 无）
- **现象**：PATCH 可把 code 改成与另一台相同；`calibration_due` 允许清空，清空后该检具在 `/api/msa` 被判预警且不能新建研究，但界面不提示原因。
- **建议**：PATCH 补 code 唯一性校验；清空到期日时明确告警；校准状态统一由“到期日 + 今天”派生。

### M-07 【中】【操作】计划公差为空时，新建研究必然被“与计划一致”拒绝

- **位置**：`server.js:4389-4416`；`lib/db.js:1279-1280`、`1311`；`public/app.js:6911`
- **现象**：`ensureMsaPlans` 在特性没有同时具备 LSL/USL 时把 `tolerance` 写成 `null`；界面新建研究总是发送 `tolerance: +value`，服务端 `+body.tolerance !== plan.tolerance` 即“数字 !== null”恒真，报“研究设计必须与计划一致，请先维护计划”；即使前端不发，服务端取 `plan.tolerance`（null）后又会报“容差必须大于 0”。
- **触发/影响**：用户无法通过研究表单自救，错误指向“研究设计”而非根因“计划缺公差”。
- **建议**：一致性校验改为 `plan.tolerance != null && +body.tolerance !== plan.tolerance`；计划公差为空时允许本次输入并写回计划；错误文案区分两种原因。

### M-08 【中】【页面】KPI 用硬编码阈值，与后端判定双口径

- **位置**：`public/app.js:6496`
- **现象**：KPI 卡按 `<10/<=30` 硬判颜色，不读 `judgment`；与 M-02 叠加后出现“红色结论 + 绿色 KPI”。
- **建议**：颜色与文案直接取后端 `judgment`；`%Tol` 与 `%GRR` 同时展示并标注主导项。

### M-09 【中】【操作】“建立台账”用 `setTimeout(...,0)` 预填新增抽屉

- **位置**：`public/app.js:6949-6958`
- **现象**：依赖下一轮事件循环读取刚渲染的 DOM 并赋值；任何渲染延迟/重绘都会导致预填为空或填错行。
- **建议**：打开抽屉时把计划对象作为参数传入渲染函数，避免“渲染后再补值”。

### M-10 【中】【逻辑】“当前计划”和“历史研究”过滤条件不一致

- **位置**：`public/app.js:6446-6600` 附近（`currentPlans` / `researchPlans`）
- **现象**：两个列表对状态、`source_status`、是否完成的过滤条件不同，同一计划可能只出现在其中一个。
- **建议**：用一个 `msaPlanView(plan)` 派生 `state`（待研究/研究中/已完成/来源失效），两个列表按状态分组而不是各自过滤。

### M-11 【中】【页面】“待建台账”伪检具与真实检具混排

- **位置**：`server.js:4229-4260`（`PLAN-<hash12>`、`planned_only:true`、`calibration_warning:true`）
- **现象**：没有检具编号的计划会合成一条伪检具并永久标预警。
- **触发/影响**：检具列表信噪比低，用户误以为真有这台设备。
- **建议**：伪检具只出现在“计划”视图并明确标注“待建台账”；补检具后自动消除。

### M-12 【中】【逻辑】P3-08 表格按中文列名正则解析，解析不到默认 10/3/3

- **位置**：`lib/db.js:1168-1344`（`/^特性$/`、`/检具编号/`、`/零件数.*人数.*次数/`、`/计划日期/`；失败默认 10/3/3）
- **现象**：交付物表头改一个字（如“零件数量”）就解析失败，计划静默变成 10/3/3；没有日志/冲突提示。
- **建议**：解析失败时生成“需人工确认”的计划并写冲突记录；列名映射做成可配置；在交付物侧校验表头。

### M-13 【中】【逻辑】来源失效只影响计划，不回退已完成研究

- **位置**：`lib/db.js:1168-1344`（重算 `source_active/source_status`）；`server.js:4229-4530`
- **现象**：CP 行编辑 → CP 降草稿 → 计划“待复核”；但已完成的 `msa_study` 仍保持“已完成/接受”，PPAP 仍可能引用。
- **建议**：来源失效时把关联研究标为“依据已失效”，并在 PPAP 就绪检查中排除。

### M-14 【低】【逻辑】没有最少零件数/评价人数提示

- **现象**：AIAG 建议 ≥10 件、≥2 人（通常 3 人），系统只校验维度一致，不提示样本代表性。
- **建议**：低于建议值时给出黄色提示（不阻断）。

### M-15 【低】【操作】切换研究维度时保留已填值

- **位置**：`public/app.js:6719-6727`
- **现象**：改零件数/人数/次数后网格重绘，已填值按索引保留，可能错位。
- **建议**：维度变化时二次确认并清空，或按“评价人-零件-次数”键迁移。

## PPAP 与基线

### B-01 【高】【逻辑】打包取“最近任意基线”，不是本次提交对应的基线

- **位置**：`server.js:5193`、`5203` 附近（`SELECT * FROM baseline WHERE project_id=? ORDER BY frozen_at DESC LIMIT 1`）
- **现象**：`POST /api/ppap/package` 不看提交记录关联的 `baseline_id`，直接取最新基线。
- **触发/影响**：提交后又在别的范围冻结了新基线，打包内容与提交时审查的内容不一致；客户收到的 ZIP 不是“提交时那一版”。
- **建议**：提交记录写入 `baseline_id`，打包严格按该基线取件；基线不可变，缺失时拒绝打包。

### B-02 【高】【逻辑】提交等级矩阵 L4 等同 L1、L5 等同 L3

- **位置**：`server.js:5190-5209`
- **现象**：`L1=[18]`、`L2=[1,4,5,6,7,8,11,14,18]`、`L4=[18]`、其余（含 L3/L5）=全部 18 项。
- **触发/影响**：等级 4 只要求 PSW、等级 5 要求全部 18 项，与 AIAG PPAP 等级定义（L4=PSW+指定文件、L5=现场审核+全部）不符；客户按等级 4 提交会被系统判“齐套”，实际缺少约定文件。
- **建议**：按 AIAG 第 4 版等级表重写矩阵，并允许项目级覆盖；页面展示每个等级的实际清单。

### B-03 【高】【逻辑】清单用实时状态、包里装基线快照，两者会矛盾

- **位置**：`server.js:5231-5249`（`missing` 用 `status==='已完成' && linked.linked_ready`）；打包逻辑读取基线快照
- **现象**：就绪清单看的是当前实时数据，打包内容来自基线快照。
- **触发/影响**：清单显示齐套，包里却缺件（基线冻结后交付物才批准）；或反之，清单显示缺件但基线里其实有。
- **建议**：清单、校验、打包统一以“目标基线”为准；实时状态只用于提示“基线后有更新”。

### B-04 【高】【逻辑】PPAP 就绪校验“只看有没有、不看行不行”

- **位置**：`server.js:5135-5188`
- **现象**：MSA 只要求计划全部完成，不看 `judgment`（“不接受”也通过）；SPC 只要求有数据集，不看 Cpk/判异；FMEA 只要求已发布，不看高 AP 决定是否仍有效。
- **触发/影响**：能力不足、测量系统不可接受的证据也能进入 PPAP 包，质量门失效。
- **建议**：就绪规则改为可配置的“质量门”：MSA `judgment='接受'`（或条件接受+书面批准）、SPC `Cpk≥目标` 且无失控、FMEA 无未关闭高 AP；不满足时阻止或要求偏差批准（写原因与批准人）。

### B-05 【中】【逻辑】基线冻结的检具/特性快照没有项目过滤

- **位置**：`lib/db.js:911+`（`freezeBaseline` 的 GAUGE/CHAR 查询）
- **现象**：快照取全库检具/特性，不是本项目引用到的那些。
- **触发/影响**：基线内容膨胀、包含无关项目数据；跨项目同名检具可能混入。
- **建议**：按 `projectGauges` / `project_char` 过滤；快照只含本项目引用对象（S-02 同源）。

### B-06 【中】【逻辑】基线不可变，但缺少“版本对比/差异说明”的完整入口

- **现象**：`baselineDiff` 存在（对象级/字段级），但页面主要展示“最新基线”，历史基线之间的对比入口有限；ECR 分支基线与主基线的关系只靠 `tag`。
- **建议**：基线列表提供“与上一版/与指定版对比”；ECR 分支基线显式记录 `parent_baseline_id` 与变更范围。

### B-07 【中】【操作】前端“先冻结再打包”，版本号随机

- **位置**：`public/app.js:7340-7371`
- **现象**：点打包时先生成基线（`version: 'V1.' + (Date.now() % 90 + 10)`），再调用打包；批准人硬编码。
- **触发/影响**：每点一次就多一个语义不明的基线；版本号不可读、不可排序；审计无法对应真实批准人。
- **建议**：打包前要求选择已有基线或显式“冻结新基线”（填写版本与说明）；版本号由服务端按语义生成；批准人取会话。

### B-08 【中】【安全】PPAP 状态变更审计固定为“质量经理 王”

- **位置**：`server.js:5195`
- **建议**：取会话用户；状态迁移加角色校验（提交/批准分离）。

### B-09 【中】【操作】证据上传直接把状态置为“已完成”

- **位置**：`public/app.js:7214-7225`
- **现象**：`saveEvidence` 固定 `status:'已完成'`，不要求审核/批准。
- **建议**：上传后置“待确认”，由质量角色确认完成。

### B-10 【中】【页面】提交等级差异在界面不可见

- **位置**：`public/app.js:7000-7420`
- **现象**：选择等级后，页面仍展示 18 项，不标出“本等级必需/可选/不适用”。

### B-11 【中】【逻辑】导出记录挂“最近基线”，与导出内容无关

### B-12 【低】【逻辑】ZIP 仅在下载时校验哈希

### B-13 【低】【页面】PPAP 18 项的“不适用/顾客 waiver”没有建模
