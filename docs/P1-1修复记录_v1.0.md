## 2. 设计

### 2.1 数据模型

`process_step` 新增列：

| 列 | 用途 | 迁移 |
|---|---|---|
| `origin_step_id` | PROCESS 工序派生自哪一条 INITIAL 工序；手工序为空 | `ensureColumn` + `CREATE INDEX idx_process_step_origin` |

派生不复制来源的层级关系字段以外的东西：`parent_step_id` 重新映射到新生成的 PROCESS 父工序，因此两层结构保持一致。

### 2.2 派生语义（幂等、不覆盖）

- 只处理**未作废的 INITIAL 工序**，按 `seq` 顺序先父后子；
- 已有 `origin_step_id` 指向它的活动 PROCESS 工序 → 跳过，不重复创建；
- 新建工序为 `草稿 / V1.0`，复制工序号、名称、类型、设备、工装、输入、输出；
- 工序号沿用初始版；若与现有 PROCESS 工序号重复，**不擅自改号**，在响应的 `step_no_conflicts` 中返回，由用户决定；
- **只补缺失，不覆盖已有过程工序**：阶段 3 的细化（拆分、补设备、调顺序）不会被重新派生冲掉。已派生后又改动的差异由一致性检查列出，由人工判断保留哪一版；
- 写审计：`派生 / process_step`，after 记录来源、创建数、跳过数与新工序 ID。

### 2.3 一致性检查语义

| 分组 | 含义 |
|---|---|
| `missing_in_process` | 初始版有、过程版没有（含被作废后需要重建的） |
| `added_in_process` | 过程版有、没有初始来源（阶段 3 自行新增 / 批量导入 / 手工录入） |
| `changed` | 已派生，但工序号、名称、类型、设备、工装、输入、输出任一不一致，附差异字段 |
| `source_obsolete` | 来源初始工序已作废或不存在，过程版仍在用 |
| `duplicate_origin` | 同一初始工序被多条过程工序引用 |
| `step_no_conflicts` | 过程版内部工序号重复 |

同时返回 `initial_doc_status`（P1-10 交付物状态）与 `consistent` 总标记。

## 5. 未覆盖与说明

| # | 事项 | 说明 |
|---|---|---|
| 1 | 派生不自动同步后续改动 | 初始版改名后，过程版不会自动跟着改；一致性检查会列出差异，需人工在 P3-04 确认（避免覆盖阶段 3 的细化） |
| 2 | 工序号重复 | 派生沿用初始版工序号；若 PROCESS 已有同号工序，只在 `step_no_conflicts` 提示，不自动改号（P-03 的编号唯一性仍属待办） |
| 3 | 下游仍只认 PROCESS | PFMEA、控制计划、SPC 的读取逻辑未改，符合“INITIAL 只作来源”的设计 |
| 4 | 浏览器交互 | 新增按钮与抽屉只做了 JS 语法与 DOM 逻辑层验证，未做人工浏览器逐屏点击 |
| 5 | P-02 选择硬阻断 | 父工序发布要求全部活动子工步已发布；未采用“发布父工序但标注不覆盖子工步”的软方案 |
