## 本模块结论

APQP 与交付物是整个系统的“证据底座”，但当前底座有三处结构性漏洞：

1. **受控文件不可信**：导出读取“当前 `data_json`”（可能是未批准草稿），版本号却沿用旧批准版本。
2. **审批状态机可绕过**：`PUT` 接受全部五态、自动保存会把“待审核/已批准”静默打回草稿、批准不校验完成度，批准人来自前端默认值。
3. **自动保存会写错对象**：定时器与 `Ctrl+S` 在视图切换后仍指向旧文档，轻则丢编辑，重则把 B 文档的数据写进 A 文档。

### A-01 【高】【逻辑】导出取当前草稿内容，却标注旧批准版本号

- **位置**：`server.js:7947-7968`（`data = JSON.parse(row.data_json)`、`version: row.version`、`subtitle` 含 `row.status`）；`server.js:7971-7977`（导出记录挂“最近基线”）；`public/app.js:1868`
- **现象**：导出接口只查 `project_doc` 当前行，内容直接取 `data_json`；批准时写入 `project_doc_revision` 的受控快照、以及 `published_version` 完全未参与。
- **触发/影响**：批准 V1.1 → 发起修订（状态回草稿、版本仍 V1.1）→ 修改并自动保存 → 下载 Word/Excel，得到的是**含未批准内容、版本号仍为 V1.1** 的文件；页面还写着“下载即生成当前版本的 Word / Excel”。这直接破坏“受控文件=批准内容”的假设。
- **建议**：导出默认取最近一次 `status='已批准'` 的 `project_doc_revision`；提供“导出草稿 / 导出批准版”两个入口；草稿文件名与页眉标注“草稿”；导出记录写入对应 revision 与基线。

### A-02 【高】【逻辑】服务端状态机没有守卫，可任意写状态

- **位置**：`server.js:7589-7662`（`PUT /api/docs/:code`）；`public/app.js:1825`、`1871-1878`、`2403`
- **现象**：
  - `allowedStatus` 含全部五态，PUT 不校验合法迁移；草稿页状态下拉含“待审核”，选中即保存，绕过 `/submit` 的审计与变更说明。
  - 草稿页切到“待审核”后页面不立即锁定（要重新进入才锁），继续输入触发自动保存；服务端发现 `contentChanged && old.status∈{待审核,已批准,已完成}` 就把状态改回“草稿”，自动保存无 toast，状态被静默回退。
  - 已批准/已完成文档的状态框被禁用，表单类交付物又没有“完成”按钮（`data-mark` 只给 `kind==='none'`），所以“已批准→已完成”在界面上不可达；反过来，调用方自带 `approved_by` 就能 PUT 成“已批准”，绕过 `/approve` 的升版与快照。INSERT 分支不写 `approved_by/approved_at/published_version`。
- **建议**：服务端用显式迁移表（草稿→待审核→已批准→已完成/修订）；PUT 只允许“未开始/草稿”；“已批准”只能由 `/approve` 产生；补“完成”入口；INSERT 补全批准字段。

### A-03 【高】【逻辑】没有乐观锁，多标签页/迟到保存 last-write-wins

- **位置**：`server.js:7611`、`7629-7637`；`public/app.js:2165-2168`
- **现象**：客户端把 `version: d.version` 发回，服务端只把它当“没传时的默认值”，从不与库中版本比较。
- **触发/影响**：两个标签页同开一份交付物，B 的旧 `state.docData` 会把 A 的内容整体覆盖；更严重的是审批期间在途的自动保存：点击批准后，1.5 秒前发出的 PUT 落地，若内容有差异就按 7626-7628 把“已批准”改回“草稿”并清空批准人。
- **建议**：`version` 作为乐观锁（`UPDATE ... WHERE version=?`，影响行数 0 → 409）；前端提示“已被他人修改，请刷新”；提交/批准时冻结版本并取消所有在途保存。

### A-04 【高】【操作】自动保存定时器与 `Ctrl+S` 监听跨视图泄漏

- **位置**：`public/app.js:208-213`（`markDirty` 闭包 `timer`）、`2148-2168`（`saveDoc` 读全局 `code`/`state.docData`/`$('#docStatus')`）、`2400`（`docBack` 不等待保存）、`422-435`（`goApqpPhase` 不经过 `go()`）、`2404-2408`、`2658-2673`（模板编辑同构）；`server.js:96-101`（`{...previous, ...data}` 合并）
- **现象/触发**：在文档 A 输入后 1.5 秒内离开：
  - 若新页面没有 `#docStatus`，定时器触发 `$('#docStatus').value` 抛 `null`，被 catch 后只弹错误 toast，**最后一次编辑丢失**；
  - 若文档 B 已渲染，旧闭包读到的是 B 的全局状态与 B 的状态框，却 PUT 到 A 的 URL，服务端按 `{...previous, ...data}` 合并，**B 的字段被写进 A**；
  - `goApqpPhase` 不走 `go()`，不移除 `docShortcutHandler`，在阶段页按 `Ctrl+S` 仍会调用已离开文档的保存；
  - 模板编辑器同样结构，旧定时器会用新模板的 `state.tplSchema` PUT 旧模板 id。
- **建议**：视图卸载统一 `clearTimeout` + `removeEventListener`；`saveDoc` 只依赖入参快照，不读全局 `state`；`docBack` 等待保存完成；用 `AbortController` 取消飞行请求。

### A-05 【高】【逻辑】模板绑定“接管”原交付物，但两份数据各算各的

- **位置**：`public/app.js:2438-2439`、`1274-1276`；`server.js:5476-5479`、`7487-7496`、`7502-7510`、`7538-7542`、`7791-7795`、`7938-7945`
- **现象**：
  - 绑定后 `GET /docs` 给原 CATALOG 行注入 `tplId`，`openDoc` 看到 `meta.tplId` 直接打开模板编辑器；原 `project_doc` 的 schema 与数据未删除，但标准编辑入口从此不可达。
  - 模板编辑写 `doc_template.schema_json`，列表行状态/完成度仍取 `project_doc`；模板也不会进入“待审核/已批准”。
  - 上传时带 `doc_code` 会跳过重复检查，同一编号可绑定多个模板；`tplByCode` 用无序 SELECT 建 Map，后一条静默覆盖。
  - 自定义模板编号（如 P4-10）不在 CATALOG：列表仍渲染 Word/Excel 按钮，点击 `/docs/P4-10/export` 抛“交付物不存在”；深链同样报错。
- **建议**：模板与交付物建立显式绑定（同一行或绑定表），模板编辑结果回写原交付物并进入同一审批链；`doc_code` 唯一约束；自定义编号的详情/预览/导出统一走 `/templates/:id`。

### A-06 【高】【逻辑】批准不校验完成度/必填/角色，批准人写死

- **位置**：`server.js:7688-7709`、`7603-7608`；`public/app.js:2342`、`2349-2352`、`2356`、`2393`；`lib/field-guide.js:115-121`
- **现象**：`/approve` 只检查状态=待审核、`approved_by` 非空、A-* 检查表与列定义；不看 `docPct`，也不校验任何字段必填。空白表单可先置待审核再批准，0% 完成度也能生成“受控版本”。`field-guide` 的必填规则只生成展示文案，服务端从未使用。批准人默认“质量经理 王”、提交人默认“张工艺”、退回人默认“质量工程师 王”。
- **建议**：批准前强制 `pct>=100` 或按字段级必填规则校验；校验审批角色且禁止编制人自批；身份从会话取；变更说明的校验放服务端。

### A-07 【中】【操作】首次提交也强制填“变更原因”，而待审核时该输入被禁用

- **位置**：`public/app.js:2333-2347`、`1871-1878`
- **现象**：提交前要求 `#docChangeNote` 非空（首次提交同样）；该输入在“待审核”状态被禁用。正常提交会先保存说明，若通过状态下拉直接进入待审核，则无法补填，只能退回。
- **建议**：首次提交不要求变更原因；锁定态用只读文本展示而不是 `disabled` 输入；校验放服务端并与提交接口合并。

### A-08 【中】【逻辑】版本历史不可回溯，且“已退回”状态不可达

- **位置**：`public/app.js:2411-2428`；`server.js:7754-7758`、`7773-7777`、`7646-7656`、`7717-7719`、`7668`
- **现象**：历史抽屉只有表格，没有“查看快照/对比/恢复”；`/revisions` 返回完整 `data_json` 但前端不用；退回只写审计、不写 revision；修订与普通保存沿用旧版本号，历史里出现多条同版本不同状态的记录；提交接口允许“已退回”，但退回实际把状态设为“草稿”，该分支永远不可达。
- **建议**：退回也写 revision（含原因）；区分“工作版本/修订号”；历史项增加快照查看、对比、恢复；删除不可达分支或让退回真正写入该状态。

### A-09 【中】【逻辑】完成度按“字段数”计，表格任一一格非空即整表算满

- **位置**：`server.js:7247-7274`（尤其 7251-7263、7267-7271）
- **现象**：普通字段每个计 1 分；表格字段也只计 1 分，`Array.some(row => row.some(cell => trim !== ''))` 为真即记满。50 行 BOM 只填 1 格，该表仍按 100% 计。
- **触发/影响**：列表进度条虚高；而批准又不看完成度（A-06），于是“100% 未批准”和“0% 已批准”同时存在。
- **建议**：按必填字段/必填列/最少行数定义权重；表格按行或按必填列计分；把完成度与批准门槛绑定。

### A-10 【中】【逻辑】预览/导出不套用检查表默认行与特性类型补全

- **位置**：`server.js:7544-7547`、`7574-7575`（页面路径会 `fillCharacteristicTypes` / `checklistData`）对比 `7799-7809`（预览）、`7950-7965`（导出）
- **现象**：页面能看到 A-* 检查表的 9 行问题、P1-11/P2-11 从 `char_master` 补出的类型列；预览和导出直接用原始 `data_json`，对应位置是空表/空列。
- **建议**：把“展示数据装配”抽成服务端函数，页面/预览/导出共用；导出前至少调用 `checklistData` 与 `fillCharacteristicTypes`；补页面/导出一致性测试。

### A-11 【中】【逻辑】DOCX 模板导出丢弃新增行、保留已删除行

- **位置**：`lib/export.js:1238-1250`、`1268-1288`；`public/app.js:2604-2607`、`2706-2729`
- **现象**：在线编辑支持“＋加行/－删末行”，但 `patchTable` 只按 `sourceRowIndexes` 回填原始 DOCX 中已存在的行；超出源行数的行被跳过，删除的行也没有从源 XML 移除。
- **触发/影响**：用户加三行、下载 Word 后文件里没有；删了行文件里仍在；界面还提示“下载时仅替换字段和表格数据”。
- **建议**：导出时克隆最后一行 XML 插入新增行、移除对应 `<w:tr>`；或在线编辑禁止增删源表格行并明确提示。

### A-12 【中】【操作】上传解析静默截断/丢信息

- **位置**：`lib/parse.js:263-264`（400×40 截断）、`237`（数值统一 `String(+v)`，日期可能变序列号）、`297-300`（DOCX 丢弃空行）；`lib/infer.js:54-60`（只取单元格最多的一张表）；`public/app.js:2512-2524`（只校验扩展名）；`server.js:5457-5458`（12MB 仅服务端限制）
- **现象**：多 sheet 静默忽略；行列超限静默截断；日期单元格可能被压成 `45123`；全空行被丢导致版式错位；前端看到“解析成功”就默认完整保留。
- **建议**：解析结果返回“忽略的 sheet/截断的行列/日期单元格”清单并在结果卡片提示；按 `numFmt` 还原日期；支持多 sheet 选择；前端也做大小校验。

### A-13 【中】【逻辑】模板映射只对 XLSX 有效，却对 DOCX 开放入口；应用会覆盖人工填写且取数错

- **位置**：`server.js:5548-5557`、`5630`、`5636`、`5593`、`5621-5622`、`5513-5524`；`public/app.js:2623-2624`、`2732-2769`
- **现象**：`vTpl` 对所有模板渲染“字段映射/按业务数据填充”，但 `/apply` 对非 grid 直接报“仅支持 XLSX 网格模板映射”；`PATCH /mapping` 对 docx 不校验单元格范围；应用时 `schema.rows[r][c].v = String(value)` 直接覆盖已填内容；`cp` 取 `ORDER BY stage LIMIT 1` 的任意阶段；`msa.study_count` 统计全库；映射批准后 schema 仍可被任意修改。
- **建议**：DOCX 隐藏或被后端拒绝映射入口；映射路径做存在性校验；应用前给差异预览与覆盖确认；`cp` 按当前交付物对应阶段取数、MSA 加项目过滤；映射批准后锁定 schema 或要求重新批准。

### A-14 【中】【操作】导出失败会把整个 SPA 导航到 JSON 错误页

- **位置**：`public/app.js:1515-1519`、`1434-1438`；`server.js:7986-7987`、`7944-7945`
- **现象**：下载用 `window.location.href` 直接导航；失败时服务端返回 `{error}`，浏览器整页显示 JSON，当前视图与未保存状态全部丢失，而 toast 已先说“正在生成”。
- **建议**：改用 `fetch` + `response.blob()`，检查状态码/`Content-Type` 后用临时 `<a download>` 保存；失败保留页面并显示服务端错误。

### A-15 【中】【操作】README 宣称的“上传模板”按钮不存在，页面也没有离开提醒

- **位置**：`public/app.js:1388`（只绑定 `#btnUpload`）、`1271`（只有逐行“上传”）、`2475`；`README.md:175`
- **现象**：`vApqp` 从不渲染 `id="btnUpload"` 的元素，`if ($('#btnUpload'))` 永远为假；列表只有逐行操作，没有批量提交/导出；`beforeunload`/路由离开守卫不存在。
- **建议**：渲染页头“＋上传模板”并明确是否绑定原编号；或修正 README；增加 dirty 状态下的离开提示；补批量操作。

### A-16 【中】【逻辑】“系统模块/活动项”被算作已完成，`activity_mark` 可直接切完成

- **位置**：`public/app.js:1497`、`6727-6729`（系统模块按存在即完成）；`public/app.js:1446-1454`（`data-mark` 直接 PUT `activity_mark:true`）；`server.js:7589-7662`（`activity_mark` 例外）
- **现象**：模块类交付物只要入口存在就计入完成度；活动类交付物用按钮在“已完成/未开始”之间切换，不要求任何证据或批准。
- **建议**：模块类不计入“已完成”，只作为导航；活动类要求填写完成日期、证据与责任人；或明确把这两类从 APQP 完成度分母中剔除。

### A-17 【中】【逻辑】状态框被禁用仍回传其值

- **位置**：`public/app.js:1824`、`2158`、`2403`
- **现象**：`#docStatus` 在已批准/已完成时 `disabled`，但 `saveDoc` 仍读 `.value` 并放入 PUT；`onchange` 监听在禁用状态永不触发。若服务端放宽校验，客户端会用它覆盖真实状态。
- **建议**：状态字段不随保存提交；或提交时只允许“未开始/草稿”。

### A-18 【低】【逻辑】自定义模板编号的深链与导出必然报错

- **位置**：`server.js:7538-7542`、`7938-7945`；`public/app.js:1274-1276`
- **现象**：不在 CATALOG 的模板编号走 `/docs/:code` 或 `/docs/:code/export` 直接抛“交付物不存在”；列表按钮也未按 `isTpl` 分流。
- **建议**：按 `isTpl` 分流到模板接口；未知编号给友好提示。

### A-19 【低】【逻辑】修订/保存写入占位变更原因

- **位置**：`server.js:7646-7656`、`7773-7777` 附近（`'变更原因待补充'`）
- **现象**：自动生成 revision 时用占位文案，历史记录出现无意义原因，事后无法追溯。
- **建议**：无原因时不写 revision 或标记“自动保存快照”；修订必须要求原因。

### A-20 【低】【操作】APQP 列表缺少批量操作

- **位置**：`public/app.js:1248-1487`
- **现象**：只能逐行编辑/上传/导出/标记完成，没有批量提交、批量导出、按阶段筛选后的批量操作。
- **建议**：增加多选与批量提交/导出；批量操作前显示影响清单。
