## 本模块结论

FMEA 的**数据模型与发布门禁设计是项目中较扎实的部分**（AP 矩阵、同 FE 下 S 一致、AP=H 必须有已批准决定、叶节点必须有正式功能和分析行）。但存在三个会直接阻断或污染分析的问题：

1. 修改既有行的 S 必然失败（一致性查询没有排除自身）。
2. 高 AP 决定的“已批准”可以由客户端直接写入，发布门禁因此可被绕过。
3. 删除 FMEA 行/节点只把 CP 行的 `fmea_row_id` 置空，不清 `cp_fmea_link`，留下孤儿引用，后续 CP 行无法删除、同步判断也失真。

PFD 侧的主要问题是**发布态可以被 `PATCH` 绕过删除保护**，以及 P1-10（INITIAL）与 P3-04（PROCESS）是两套互不相通的数据。

## FMEA

### F-01 【高】【逻辑】修改既有行的严重度必然失败

- **位置**：`server.js:2873-2877`
- **现象**：`SELECT s FROM fmea_row WHERE fmea_id=? AND fe_id=? AND s<>? LIMIT 1` 没有排除当前 `row_id`。
- **触发/影响**：任何对已存在行修改 S（包括三场景重算后 S 变化）都会命中自身，抛出“同一失效影响下已存在 S=… 必须一致”。结果是**严重度一旦录入就不可修改**，只能删行重建（又会丢措施与决定）。对照紧随其后的重复行查询（2878-2881）正确带了 `row_id<>?`。
- **建议**：改为 `... AND row_id<>?` 并传入 `body.row_id || ''`；补一条“编辑行 S”回归测试。

### F-02 【高】【逻辑】前端 AP 矩阵是硬编码镜像，兜底值与后端不一致

- **位置**：`public/app.js:4651-4667`；`server.js:2830`（`DB.apLookup`）
- **现象**：前端用一张硬编码的 AP 矩阵计算并展示 AP，查不到时兜底 `'M'`；后端从 `ap_matrix` 表查，查不到时回退 `AP_BANDS`，最后兜底 `'?'`。
- **触发/影响**：前端显示 AP=中、后端保存 AP=高（或反之），用户按显示结果判断是否需要措施；AP=H 的发布门禁按后端值执行，出现“页面说不用处理、发布却被拦”。
- **建议**：AP 只由后端计算并随行返回；前端不重复实现；若必须离线展示，由接口下发矩阵版本与表体。

### F-03 【中】【逻辑】AP 矩阵种子用裸 INSERT，中断后永久缺格

- **位置**：`lib/db.js:533-538`；`lib/db.js:358-370`
- **现象**：1000 格用 `INSERT` 逐条写入，`k` 是主键；若初始化中途失败，下次启动不会补（seed 只在项目不存在时执行），`apLookup` 静默回退到 `AP_BANDS`。
- **触发/影响**：同一 S/O/D 在不同安装上可能得到不同 AP；缺格区域无任何告警。
- **建议**：改为 `INSERT OR IGNORE`，启动时校验 `COUNT(*)=1000` 并自愈；`apLookup` 查不到时记录告警而不是静默回退。

### F-04 【高】【安全/逻辑】高 AP 决定的“已批准”可由客户端直接写入

- **位置**：`server.js:3479-3511`（`POST /api/fmea/decision`）
- **现象**：`status` 从请求体取（`'已批准'` 直接接受），`approved_by` 只校验非空字符串，没有角色校验、没有“批准人≠编制人”约束；审计固定写 `'质量经理 王'`。
- **触发/影响**：任何能调用接口的人都能把 AP=H 的决定标成已批准，随后 `/fmea/publish` 的门禁（3518-3525）全部通过。发布门禁形同虚设。
- **建议**：决定的状态迁移由服务端控制（提交→待评审→批准）；批准需 `quality`/`admin` 角色且不得为提交人；审计取会话用户。

### F-05 【中】【逻辑】S/O/D 变更后旧决定不失效

- **位置**：`server.js:3498-3507`（`ON CONFLICT(row_id) DO UPDATE` 只覆盖字段）；`server.js:3518-3525`（发布只检查 `status='已批准'`）
- **现象**：决定与行是一对一，但决定没有记录“基于哪一版 S/O/D/AP”；行修改后决定仍为已批准，发布照样通过。
- **触发/影响**：原来 AP=H 的措施针对旧失效原因，改版后措施已不对应，却仍被视为“已处置”。
- **建议**：决定表记录 `s/o/d/ap` 快照；行变更使决定回到“待评审”；发布时比对快照。

### F-06 【高】【逻辑】删除 FMEA 行/节点会留下孤儿 CP 链接，且不降级控制计划

- **位置**：`server.js:3324-3331`、`3364-3367`、`3391-3395`（只 `UPDATE cp_row SET fmea_row_id=NULL`）；`lib/control-sync.js:24/202/236/288`（`cp_fmea_link`）
- **现象**：删除行时清空 `cp_row.fmea_row_id`，但**不删除 `cp_fmea_link` 中对应记录**；也不把受影响的 CP 打回草稿，只写一条 FMEA 审计。
- **触发/影响**：
  - `server.js:3712` 删除 CP 行时检查 `cp_fmea_link`，孤儿链接会让 CP 行**永远无法删除**；
  - `control-sync.js:202` 用 `EXISTS(cp_fmea_link)` 判断是否保留人工维护的 CP 行，孤儿链接导致同步逻辑误判；
  - CP 仍显示为已批准，但其依据已被删除，PPAP 证据链断裂。
- **建议**：删除 FMEA 行/节点时同步清理 `cp_fmea_link`；受影响 CP 行标记“依据失效”并触发 `markCpDraft`；在删除确认框中列出受影响 CP 行。

### F-07 【中】【操作】“必填 PC/DC”阻断七步法的渐进填写

- **位置**：`server.js:2864-2871`
- **现象**：FE/FM/FC + 现行预防控制 + 现行探测控制全部必填才能保存一行。
- **触发/影响**：七步法前期（结构/功能分析阶段）无法先记录失效链再补控制；用户只能填占位符，反而污染数据。
- **建议**：区分“草稿行”和“可发布行”；草稿允许缺 PC/DC，发布时再强制。

### F-08 【中】【逻辑】改名会新建节点，旧节点成为孤立失效节点

- **位置**：`server.js:2845-2854`（`resolve` 文本不变才复用 id）、`2802-2815`（`findNode` 按 name 精确匹配）
- **现象**：把 FE 从“阻值超差”改为“阻值偏移”时，新节点被创建，旧节点保留；孤立节点清理只在删除行/节点时执行。
- **触发/影响**：结构树越用越乱，历史失效节点混在候选列表里；后续同名匹配可能命中旧节点。
- **建议**：编辑文本时优先“重命名当前节点”，只有明确“新建”才建节点；增加孤立节点清理任务与 UI。

### F-09 【中】【操作】FMEA 发布后编辑任一行会静默回草稿

- **位置**：`server.js:2924/2937/3509` 等（`UPDATE fmea_header SET status='草稿'`）
- **现象**：行、功能、措施、决定的任何修改都把表头改回草稿，前端只提示保存成功，不提示“已发布版本失效”。
- **建议**：返回并提示“FMEA 已回到草稿，需重新发布”；保留已发布版本快照以便对比。

### F-10 【中】【操作】删除结构节点级联删除分析行/措施/决定，确认信息不足

- **位置**：`server.js:3307-3353`
- **现象**：删除一个结构节点会递归删除所有子孙节点及其下所有分析行、措施、决定，仅返回节点数与行数；前端确认框是否展示这些数量需确认（当前接口返回值足够，但 UI 未必使用）。
- **建议**：删除前先调用“影响预览”接口，明确列出将删除的行、措施、被清空的 CP 关联；二次确认需输入节点名。

### F-11 【低】【逻辑】只传 `s` 不传三场景时，场景字段为空

- **位置**：`server.js:2821-2827`、`2916-2923`
- **现象**：`s = max(sp, ss, su, body.s)`，但 `s_plant/s_ship/s_user` 按传入值原样写入，可能全为 `null`。
- **触发/影响**：行表 S 有值、三场景列为空，详情/导出显示空白，无法解释 S 的来源。
- **建议**：至少要求一个场景值，或根据 `s` 回填到最严重场景并标注“未分场景评级”。

### F-12 【低】【逻辑】行 ID 生成每次全表扫描

- **位置**：`server.js:2907-2911`
- **现象**：`SELECT row_id FROM fmea_row WHERE row_id LIKE 'FR-PF-%'` 取全部再在 JS 求最大。
- **建议**：改用 `SELECT MAX(CAST(substr(row_id,7) AS INTEGER))` 或独立序列表。

## PFD

### P-01 【高】【逻辑】`PATCH` 可直接把被引用的工序置为“作废”，绕过删除保护

- **位置**：`server.js:2682-2693`（`fields` 含 `status`，无引用检查）对比 `server.js:2697-2715`（`DELETE` 检查 FMEA/CP 引用）
- **现象**：`DELETE /api/steps/:id` 会检查 `fmea_row` 与 `cp_row` 引用并拒绝；但 `PATCH {status:'作废'}` 只做 `validateStepForPublish`（仅发布时）就直接写入。
- **触发/影响**：已被 PFMEA/控制计划引用的工序可以被“作废”，而引用方仍指向它；后续 `GET` 列表过滤掉作废工序，CP/FMEA 显示工序名为空，PPAP 仍可能通过。
- **建议**：状态迁移统一走 `PATCH` 时也执行引用检查；作废改为专用接口并记录影响面；作废后同步把引用方标记为“依据失效”。

### P-02 【中】【逻辑】发布父工序不检查子工步是否已发布

- **位置**：`server.js:2675-2689`、`2519-2529`
- **现象**：`validateStepForPublish` 只校验当前工序的名称/工序号/类型/设备/输入输出；父 OP 可以在子工步仍是草稿时发布。
- **触发/影响**：控制计划可引用已发布父工序，但其细分工步尚未受控；“已发布”的含义在不同层级不一致。
- **建议**：发布父工序要求所有子工步已发布（或明确“父工序发布不覆盖子工步”并在 UI 标注）。

### P-03 【中】【逻辑】工序号可任意填写，无唯一性校验

- **位置**：`server.js:2648-2651`（`body.step_no || 自动生成`）
- **现象**：允许客户端直接指定 `step_no`，不校验格式与重复；排序接口会重排工序号，但普通新增不会。
- **触发/影响**：同一 PFD 出现两个“010”，下游 CP/FMEA 按工序号展示时无法区分。
- **建议**：同一 `project_id + pfd_mode` 下 `step_no` 唯一约束；自定义编号校验格式；冲突时返回明确错误。

### P-04 【中】【逻辑】PFD 没有版本历史，撤回再发布会丢失上一版内容

- **位置**：`process_step` 表（`ver/published_at/published_by/change_summary` 单行覆盖）；`server.js:2675-2681`
- **现象**：发布时版本号自增、时间/人覆盖写；撤回后编辑再发布，上一版内容不可回溯，也没有 revision 表。
- **建议**：增加 `process_step_revision` 快照；发布/撤回写历史；提供版本对比。

### P-05 【中】【安全】发布人来自请求体

- **位置**：`server.js:2679`（`published_by = body.user || '工艺-张'`）
- **现象**：任何调用方可指定发布人。
- **建议**：取会话用户；历史数据按审计表回填。

### P-06 【高】【逻辑】P1-10（INITIAL）与 P3-04（PROCESS）是两套互不相通的数据

- **位置**：`lib/deliverable-sync.js:1073-1075`（P1-10 写入 `pfd_mode='INITIAL'`）；`lib/control-sync.js:80/154/191/243/251`（只读 `pfd_mode='PROCESS'`）；`lib/doctpl.js:500/527`
- **现象**：阶段 1 的初始流程图与阶段 3 的过程流程图各自独立建工序，没有“从初始流程派生/继承”的关系；下游 PFMEA、CP、SPC 只认 PROCESS。P1-10 的完成对主线没有任何数据贡献。
- **触发/影响**：咨询师在阶段 1 精心拆的工序路线，到阶段 3 要重新录入；两套工序号/名称不一致时无人发现。这是“APQP→PFD→PFMEA→CP”主线的第一处断点（详见主报告第四章）。
- **建议**：P3-04 提供“从 P1-10 生成”动作，保留 `origin_step_id`；INITIAL 步骤作为 PROCESS 步骤的父级或来源；一致性检查覆盖两层。

### P-07 【高】【逻辑】批量导入“替换”模式直接作废全部在用工序，不做引用检查

- **位置**：`server.js:3209-3257`（`POST /api/steps/bulk`，`mode !== 'append'` 时循环 `UPDATE process_step SET status='作废'`）
- **现象**：一键导入会作废当前 PFD 的全部在用工序，**不检查 FMEA 行/控制计划行的引用**（与 `DELETE /api/steps/:id` 的保护逻辑完全相反），然后插入新工序。
- **触发/影响**：已在 PFMEA、CP 中引用的工序瞬间全部作废；FMEA 行的 `step_id`、CP 行的 `step_id` 指向作废工序，列表按“非作废”过滤后显示为空；CP 仍为已批准，PPAP 仍可提交。这是比 P-01 影响面更大的一条“静默破坏主线”的路径。
- **建议**：替换模式先做引用检查并给出影响清单；若确实要替换，需先把引用迁移到新工序或显式确认“解除引用”；作废后同步把相关 FMEA/CP 置为草稿并写审计。

### P-08 【低】【页面】工序矩阵与详情切换的可用性问题

- **位置**：`public/app.js:4869-4900` 附近（矩阵/详情切换）、`4839-4867`（结构树）
- **现象**：点击左侧工序切换到右侧详情后没有保留滚动位置与焦点；返回矩阵会重置；树节点没有键盘可操作性（`button` 有，但详情区无焦点管理）。
- **建议**：记录并恢复滚动位置；切换后把焦点移到详情标题；为树提供方向键导航。
